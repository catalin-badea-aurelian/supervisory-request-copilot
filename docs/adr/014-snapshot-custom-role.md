# ADR 014: A narrow custom role for run snapshots on `spb_snapshots`

- **Status:** accepted, applied on the showcase project (M3, 2026-11-26)
- **Context milestone:** M3 (guarded data access, snapshots)

## Context

Every run snapshots the source tables it may read into `spb_snapshots`, with an expiration
(ARCHITECTURE §7.4). The M1 live probe showed that dataset-level WRITER is not enough:
`spb-copilot` with WRITER could create a snapshot, but not one with `expiration_timestamp`, and
it could not drop one. Both need `bigquery.tables.deleteSnapshot`, which the basic WRITER role
lacks.

Two options were considered:

1. Dataset-level OWNER for `spb-copilot` on `spb_snapshots` only. It is simple, but OWNER also
   allows changing the dataset's access list, deleting any table and updating any data.
2. A custom role, bound on `spb_snapshots` only, with just the permissions the snapshot
   lifecycle needs.

## Decision

Option 2. The custom role `projects/<project>/roles/spbSnapshotManager` (title "SPB snapshot
manager", stage GA) has exactly these permissions:

| Permission | Why |
|---|---|
| `bigquery.datasets.get` | resolve the dataset |
| `bigquery.tables.create` | required to create a snapshot table |
| `bigquery.tables.createSnapshot` | create a table snapshot |
| `bigquery.tables.deleteSnapshot` | set an expiration on a snapshot; drop a snapshot |
| `bigquery.tables.get`, `bigquery.tables.list` | verify a stored snapshot still exists (rerun) |
| `bigquery.tables.getData` | query the snapshots during the run |

It is bound to `spb-copilot` **on the `spb_snapshots` dataset only**. Afterwards, the copilot's
basic WRITER entry on that dataset was removed. Its project-level role stays
`roles/bigquery.jobUser`. The role and its permissions live in `infra/bigquery/spec.py`
(`SNAPSHOT_ROLE_*`, `DATASET_IAM_BINDINGS`), and `ACCESS["snapshots"]` is now empty, so
`make bq-setup` no longer re-adds WRITER.

### How it was applied

Each step was shown to the project owner as an exact plan and applied only after their
separate approval (`scripts/iam_snapshot_role.py`, which prints only unless given `--apply`):

- **A.** `gcloud iam roles create spbSnapshotManager --project=<project> ... --stage=GA`
- **B.** `GRANT \`projects/<project>/roles/spbSnapshotManager\` ON SCHEMA \`<project>.spb_snapshots\`
  TO "serviceAccount:spb-copilot@<project>.iam.gserviceaccount.com"`, run as the owner.
  The originally planned `bq add-iam-policy-binding` on the dataset was refused with "This
  feature requires allowlisting" (and so is dataset `getIamPolicy`). The DCL statement is
  equally dataset-scoped. It shows up as a dataset access entry whose role is the custom role.
- **C.** Probe: `verify-iam --only snapshots` (create with expiration, query, drop).
- **D.** Remove the WRITER access entry for `spb-copilot` on `spb_snapshots`. No other entry is
  touched.

Rollback, in reverse order: re-add the WRITER entry; `REVOKE` the role `ON SCHEMA` the dataset;
`gcloud iam roles delete spbSnapshotManager`. `python scripts/iam_snapshot_role.py --rollback`
prints the commands.

## Consequences

**Proven on the live project** (`make verify-iam`, 24/24 PASS):

- `spb-copilot` creates snapshots of every pack source with an expiration, queries them and
  drops them. It does this with the custom role alone (`tests/data/test_snapshots_bigquery.py`).
- It still cannot write `spb_raw`, `spb_group` or `spb_control`: append and create table both
  return 403.
- In `spb_snapshots`, it cannot append data to an ordinary table, cannot insert into one with
  DML, and cannot delete one: all three return 403.

**Residual permissions (accepted, stated plainly):**

1. **`spb-copilot` can create an ordinary (empty) table in `spb_snapshots`.**
   `bigquery.tables.create` is required to create a snapshot, and BigQuery offers no permission
   that allows snapshots only. The probe confirms this every time verify-iam runs. Such a table
   can hold no data written by the copilot, because it has no `bigquery.tables.updateData`, and
   the copilot cannot delete it, because it has no `bigquery.tables.delete`. The risk is clutter
   in one dataset, not data exfiltration or tampering. The project owner removes such tables;
   verify-iam removes its own probe table as the owner.
2. **`spb-copilot` can delete any snapshot in `spb_snapshots`**, including those of other runs,
   because `deleteSnapshot` is dataset-wide. A deleted snapshot makes that run's rerun fail fast
   (`SnapshotError`) instead of reproducing silently wrong numbers. The run manifest and audit
   log still record the result hashes. Snapshots also expire on their own after
   `COPILOT_SNAPSHOT_EXPIRATION_DAYS` (default 90).
3. **Snapshot DDL is not SELECT.** The copilot identity sends exactly one kind of non-SELECT
   statement: `CREATE SNAPSHOT TABLE`, generated by `copilot.data.snapshots` from the pack, never
   from agent or user input, and not routed through the SELECT-only SQL policy. Agents and the
   MCP server have no tool that reaches it.

**Observation during the probe:** removing the WRITER entry took about a minute to take effect.
The first negative probe, run immediately after step D, still succeeded in writing to and
deleting the probe table; a rerun a few minutes later was denied as expected. The probe table
had no table-level grants. Run verify-iam a few minutes after any IAM change.

**In an enterprise setting** this would be an organisation-level custom role managed in
infrastructure-as-code. Snapshots could also be taken by a separate snapshot service identity,
so the identity that reads data never holds `deleteSnapshot`.
